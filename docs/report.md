whole-body re-identification across multiple cameras.

Code: `https://github.com/a2f9f4b4-bd11-4d15-b922-8b260990d71f/missing-person-tracing`

---

## 1. Problem

When someone goes missing, the first hours matter most, but reviewing CCTV is
manual: a person scrubs through hours of footage from each camera in turn.
Faces in CCTV are usually small, blurred, or turned away, so face recognition
alone misses most sightings.

This project takes the opposite approach. It matches people by **whole-body
appearance** — clothing, build, colour — which survives low resolution and
works when the face is never visible. Given one photo, it returns a ranked
shortlist of sightings with thumbnails and playable clips, so a reviewer checks
minutes of video instead of hours.

The system never identifies anyone. It answers one question: *does this person
appear anywhere in this footage, and if so, when and on which camera?*

## 2. What was built

A local pipeline in Python 3.12, running entirely on one desktop with no cloud
services.

```
cameras / files  →  MediaMTX  →  ingest worker (one process per camera)
                                 ├ sample frames at 10 fps
                                 ├ YOLO26 detects people
                                 ├ ByteTrack follows each person
                                 └ OSNet embeds the tracklet  →  Postgres + pgvector
                                                                        ↓
                                              reference photo → same embedding path
                                                              → cosine search
                                                              → threshold + timing check
                                                              → ranked results in a web UI
```

The central object is a **tracklet**: one continuous sighting of one person on
one camera, reduced to a 512-dimension appearance vector plus a thumbnail and a
clip. Searching is then a nearest-neighbour query over those vectors.

**Components.** Ingest (recorded files and live RTSP), detection and tracking,
re-identification, a Postgres/pgvector store, a search service applying a
similarity threshold and a physical-plausibility filter, a server-rendered web
UI (FastAPI + Jinja2 + HTMX), and a retention job.

## 4. Evaluation

Measured in three tiers, each answering a different question. All figures come
from scripts in the repository and are regenerated by `scripts/eval_table.py`.

### Tier 1 — the re-ID model alone, on Market-1501

| Weights | Rank-1 | Rank-5 | mAP | Queries |
|---|---|---|---|---|
| `osnet_ain_x1_0` (MSMT17) | **70.35%** | 84.41% | 43.71% | 3,362 |
| `osnet_x1_0` (MSMT17) | 66.75% | 81.02% | 40.52% | 3,362 |

**This is a cross-domain evaluation.** The weights were trained on MSMT17 and
evaluated on Market-1501, so the correct comparison is the cross-domain
literature, *not* the widely quoted ~94% rank-1 figures, which assume training
on Market-1501 itself. Comparing against those would badly misrepresent the
result.

The AIN variant — a domain-generalisation version by the same authors — beat the
plain model by 3.6 points of rank-1, so it became the configured default. This
matches its design intent: AIN exists for deployment on cameras it has never
seen, which is exactly this use case.

### Tier 2 — the whole system, end to end

Market-1501 identities were injected as tracklets and searched through the real
API, so this measures crop selection, mean-of-crops embedding, the threshold and
the timing check — not just the model.

Tuned on **`bounding_box_train` (751 identities)**, which is disjoint from the
`query`/`bounding_box_test` identities Tier 1 reports. 150 held-out
cross-camera queries against 1,315 gallery tracklets from 400 identities.

| τ (threshold) | Top-1 | Top-5 | Wrong matches returned |
|---|---|---|---|
| 0.50 | 69.3% | **85.3%** | 467 |
| 0.65 | 69.3% | 85.3% | 457 |
| 0.70 | 69.3% | 84.0% | 403 |
| 0.74 | 68.0% | 81.3% | 314 |
| 0.78 | 60.0% | 68.7% | 205 |
| 0.82 | 48.0% | 54.0% | 94 |
| 0.90 | 10.0% | 11.3% | 5 |

**A methodological note worth recording.** An earlier version of this evaluation
tuned τ *and* selected the model on the same split it reported from. That
produced a top-1 of 100% — which looked excellent and was meaningless. Once the
tuning moved to disjoint identities, the honest figure was **69.3%**. The
discrepancy is the measurement of how much a test-set leak flatters a result.
The table generator now marks the tier-2 table "LEAKED" if the splits ever
overlap again.

**Threshold choice.** τ was set to **0.50**, favouring recall. Top-5 recall
falls from 85.3% to 81.3% between τ=0.50 and τ=0.74, while the false-positive
count falls from 467 to 314. For this problem the trade is asymmetric: a
reviewer will happily discard a few wrong thumbnails, but a missed sighting
means the system reports that a missing person was never there. Recall is the
metric that matches the product's purpose.

| Median time to searchable | **2.13 s** |
| Worst case | 2.18 s |

Measured from the moment a person leaves frame to the moment their sighting is
searchable. Earlier runs under heavier load, including two concurrent workers,
gave a median of 2.2–2.5 s and a worst case of 3.9 s — still comfortably inside
the requirement.

The latency is dominated by the 2-second lost-track timeout, not by compute.
Running on GPU instead of CPU barely changed it (2.12 s vs 2.24 s median), which
means GPU headroom buys more cameras or higher resolution, not lower latency.

| GPU (ROCm), 768×432 | 28.5 |
| GPU, 720p, one worker | 14.1 |
| GPU, 720p, two workers | 11.4 + 11.5 = 22.9 aggregate |

Two worker processes produce more aggregate throughput than one, so a single
worker does not saturate the GPU. Two cameras at 10 fps need 20 fps aggregate,
leaving roughly 15% headroom.

## 5. Does the signal actually work?

Before building the system, OSNet embeddings were measured directly on tracked
crops to check the core premise:

| | Cosine similarity |
|---|---|
| Same person, two halves of one track | 0.791 – 0.903 (mean 0.842) |
| Different tracks | max 0.873 (mean 0.720) |

Same-person similarity clearly exceeds different-person similarity, confirming
the approach. The measurement also **overturned a planned parameter**: the
technical spec proposed starting with τ = 0.5 as a conservative value, but every
observed pair scored above 0.5, so that threshold would have filtered nothing at
all. The real operating range is 0.6–0.9.

## 6. Privacy and ethics

The design treats privacy as a constraint, not an afterthought.

- **Search starts from a photo.** There is no way to browse everyone seen; the
  system has no concept of identity, only appearance vectors.
- **No labels on non-matches.** People detected but not matched are never named,
  tagged, or linked across searches.
- **Human in the loop.** Every result is a suggestion with a score. A reviewer
  confirms or rejects each one; the system never asserts a match.
- **Retention.** Footage, sightings and clips auto-delete after 3 days.
  Reference photos are deleted when a search is closed. Evaluation data is
  explicitly flagged so it survives, which keeps the deletion job from silently
  destroying the labelled set.
- **Local only.** All processing runs on one machine. No video or photo is sent
  to any external service.
- **Known bias.** Accuracy drops with changed clothing, lighting and camera
  angle. Because matching is clothing-driven, a change of jacket defeats it —
  stated here rather than hidden, since it bounds what the system can honestly
  claim.

## 7. Limitations

Stated plainly, because they bound what the results mean.

**The ≥80% top-1 target was not met.** The honest figure is 69.3% on
Market-1501 identities. The earlier 100% was a test-set leak, not a result.

**Evaluation on own footage was not completed.** Filming volunteers at two
physical locations did not happen within the schedule, so all accuracy figures
come from public datasets. Whether these numbers transfer to a specific camera
setup is untested — and transfer is exactly where re-ID is weakest.

**One subject.** With no volunteers available, there was no way to measure
cross-identity confusion on own cameras. The Market-1501 distractor gallery is a
reasonable substitute, but its crops are dataset-clean rather than captured
through this pipeline.

**Face matching (R12) was not built.** At CCTV distances a face occupies
20–40 pixels, well below the ~112×112 that face recognition needs. The system
is therefore unsuitable for close-range identification, where face recognition
would be the right tool.

**Hardware paths are untested.** The Raspberry Pi camera node scripts and the
iPhone SRT stream were written but never run against the physical devices. Live
testing used a USB webcam and replayed file streams.

**Text search is threshold-fragile.** CLIP text-image similarities vary by
prompt (top matches 0.25–0.35 against gallery medians of 0.17–0.23), so a fixed
threshold is thin. A relative rule — top-k with a floor — would be sturdier.

## 8. What I would do differently

**Measure before designing around a number.** The τ = 0.5 default in the
technical spec was a guess that a 20-minute experiment disproved. Several later
decisions would have been cheaper if that measurement had come first.

**Never tune on the reported split.** The leak that produced a 100% result was
invisible in the output — the numbers simply looked good. Only separating the
splits revealed it. Any evaluation worth reporting needs that separation built
in from the start, not retrofitted.

**Film early.** Volunteer footage was on the critical path for every
own-footage number, and it was the one dependency that could not be
parallelised or substituted. It should have been scheduled first, not last.

## 9. Conclusion

The system does what it set out to do: one photo narrows a large set of detected
people down to a short, ranked list a reviewer can check in minutes, across
recorded files and live cameras, with sightings searchable about 2 seconds after
a person leaves frame — five times better than the 10-second requirement.

The accuracy target was missed. 69.3% top-1 means roughly one search in three
puts the right person below first place, though 85.3% top-5 means they are
usually still on the first screen of results — which, for a tool whose job is to
narrow a search rather than to decide it, is the more relevant figure.

The most valuable outcome was not the system but the measurement discipline: a
threshold that would have filtered nothing, a model choice that reversed under a
fair test, and an accuracy figure that fell from 100% to 69% once the leak was
removed. Each was invisible until measured properly.
